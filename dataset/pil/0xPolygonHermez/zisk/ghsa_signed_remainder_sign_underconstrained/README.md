## Running

Scripts support two modes controlled by the `ZKBUGS_MODE` environment variable:

- **`original`** (default): compiles the project's main circuit from the full codebase.
- **`direct`**: compiles an isolated wrapper (`circuit.circom`) that only instantiates the vulnerable template.

```bash
# Setup (run once)
./zkbugs_setup.sh

# Compile only (no zkey ceremony)
./zkbugs_compile.sh                        # original mode
```

## Short Description of the Vulnerability

The arith state machine verifies signed division on magnitudes and carries the operand signs as boolean flags (na, nb, np, nr) validated by a lookup into a table generated by the ArithTable airtemplate. RISC-V requires the remainder to take the sign of the dividend. In the generated table that rule appears only for the division-by-zero case (documented at arith_table.pil:144, enforced by `np != nr` at L150); on the normal signed path the only relation between the two flags is `if (!np & nr) continue` (L163), i.e. nr <= np. For a negative dividend (np = 1) nr is therefore free. The row with nr = 0 has to exist, because an exact division has a zero remainder whose sign is positive, but nothing bound nr = 0 to the remainder actually being zero. The magnitude identity a*b + d = c and the bound |d| < |b| in arith.pil both operate on absolute values, so neither rejects the wrong sign. A sibling instance of the same gap affects the quotient sign na (DIV(1, -1) provable as +1); both are fixed by the same commit.

## Proposed Mitigation

Fixed in PR #1228 (commit 683e6d9, released in v1.1.0-alpha). Two witness columns result_is_zero and remainder_is_zero are added and bound to the values they name in arith.pil (`remainder_is_zero * div * sum_all_ds === 0` at L241, `result_is_zero * div * sum_all_as === 0` at L240), and arith_table.pil then encodes the sign rules as full truth tables over those flags: neg_remainder = neg_dividend AND NOT remainder_is_zero (L360-364 of the fixed file), with the analogous table for neg_quotient. Rejecting np != nr outright is NOT a correct fix: it also rejects honest exact divisions, whose remainder is zero and therefore positive.
