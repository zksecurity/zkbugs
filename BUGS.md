#### Short Description of the Vulnerability

#### Short Description of the Vulnerability

The `CreditVerifier` template proves knowledge of a `CreditNoteProof` by showing that a commitment `H(nullifier, secret, pubCreditType)` is in the credit Merkle tree and revealing a matching `pubNullifierHash`. The circuit has no binding to the spender or to a specific spend intent: it only exposes `pubRoot`, `pubCreditType`, and `pubNullifierHash` as public inputs. Because the on-chain `_verifyProof` function in `ArianeeIssuerProxy.sol` accepts the `CreditNoteProof` as a transaction argument without checking it against the transaction sender or an intent hash, anyone observing a valid proof in the mempool can front-run the legitimate spend by submitting the same `CreditNoteProof` themselves, burning the same nullifier and stealing the credit. The fix requires binding the proof to a spender-controlled value such as a `pubIntentHash` signal inside `CreditVerifier`, analogous to the `pubIntentHash` already present in `ownershipVerifier.circom`, so that the proof can only be spent by the intended caller.

#### Proposed Mitigation

Add a `pubIntentHash` (or equivalent spender-bound) public input to the `CreditVerifier` template and pass the caller's intent from `ArianeeIssuerProxy` through to `ArianeeCreditNotePool` so that the verifier re-checks it. Alternatively, fold `CreditVerifier` into the `OwnershipVerifier` as a single proof whose `pubIntentHash` binds the credit spend to a specific call, preventing front-runners from replaying the proof.
